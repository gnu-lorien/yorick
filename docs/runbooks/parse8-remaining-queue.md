## 1. Teach `instanceof Backbone.Model` about `Parse.Object`

**Root cause.** Backbone 1.1.2 decides "already a model, or a raw attribute hash?" with `attrs instanceof Model` at `public/scripts/lib/backbone.js:690` and `:916`; a parse@8 `ParseObject` fails that test, so every object added to or reset into a `Parse.Collection` is silently replaced by `new this.model(theParseObject)`. parse@8's `set` walks the bag with `for (const k in changes)` (`public/scripts/lib/parse-8.6.0.js:43540`), so the clone's "attributes" become `className`, `_objCount`, `_localId`, `_compatPending`, `changed`, `_compatPrevious`, `__compatEventsApplied` — and `:43546-43547` copies `id` across, so with single-instance state on those junk SetOps land on the real row and get PUT to the server.

**Parse 1.5 behaviour being restored.** `public/scripts/lib/parse-1.5.0.js:6851-6862`, `_prepareModel: function(model, options) { if (!(model instanceof Parse.Object)) { … model = new this.model(attrs, options); … } else if (!model.collection) { model.collection = this; } return model; }` — the guard was `Parse.Object`, not `Backbone.Model`, and `add` funnelled every item through it (`:6564`), then indexed the *same* object (`:6587`).

**Change.** `public/scripts/lib/parse-compat/collection.js` — inside `makeParseCollection(Parse)` (Backbone and Parse are both in scope; extract it as an exported `patchBackboneInstanceof(Parse)` and call it from `install()` at `public/scripts/lib/parse-compat/index.js:96`, next to `applyEvents(Parse.Object)`, so it does not sit behind the `if (!Parse.Collection)` guard at `index.js:101`):

```js
if (Backbone.Model &&
    !Object.getOwnPropertyDescriptor(Backbone.Model, Symbol.hasInstance)) {
  Object.defineProperty(Backbone.Model, Symbol.hasInstance, {
    configurable: true,
    value: function (inst) {
      return (Parse && Parse.Object && inst instanceof Parse.Object) ||
             Backbone.Model.prototype.isPrototypeOf(inst);
    }
  });
}
```

The `Parse && Parse.Object &&` guard is not optional: `collection.js` is deliberately loadable with a falsy Parse (`model: Parse && Parse.Object`, `collection.js:53`), and a bare `instanceof undefined` would make *every* `instanceof Backbone.Model` in the process throw.

Also add, in the wrapped `proto.set` at `public/scripts/lib/parse-compat/events.js:174`, the 1.5 normalisation from `parse-1.5.0.js:5269-5271`:

```js
if (key instanceof ParseObject) { key = key.attributes; }
```

This is belt-and-braces once `Symbol.hasInstance` is in (it closes `backbone.js:703`'s merge branch and any app code that hands a Parse object to `set`). Do **not** ship it *instead of* the `hasInstance` patch: on its own, `_prepareModel` would then build `new Sub(source.attributes)`, which carries no `objectId`, and the collection fills with id-less duplicates.

**Why the compat layer, not app code.** 12 `Parse.Collection` subclasses, reachable via `add`, `reset` and `fetch({add:true})` in all of them.

**Verify without the suite.**
- Add contract tests to `test/parse-compat-collection.test.js` and run `npm run test:node`. **The existing stub is why this slipped through** — `test/parse-compat-collection.test.js:37-38` does `PObject.prototype = Object.create(Backbone.Model.prototype)`, i.e. the stub *is* a Backbone.Model. New tests must use a stub that is not, or better, the real `public/scripts/lib/parse-8.6.0.js`.
- Assertions that reproduce all eight failures: (a) `c.add(obj); c.models[0] === obj` for both a saved and an unsaved object; (b) `c.reset([obj]); obj._getSaveJSON()` is `{}` — no `className` / `_objCount` / `_compat*` / `__compat*`; (c) run `Character._propagate_experience_notation_change`'s arithmetic (`public/scripts/app/models/Character.js:521-524`) over a one-member collection and assert `experience_earned === 30`, not `NaN`.
- After the next real run, `logs/parse-server.err.*` should contain **zero** `Invalid field name: _compatPending.` (256 occurrences today) and zero `Invalid field name: _objCount.`

**Clears:** 8 — `creation-vampire.spec.js:301` (155), `creation-werewolf.spec.js:386` (190), `creation-changeling.spec.js:508` (216), `xp-history.spec.js:522` (54), `admin-patronage.spec.js:237` (03), `long-texts.spec.js:352` (285), `access-control.spec.js:812` (388), `troupes.spec.js:540` (130). Plus it is a precondition for item 2's two.

**Risk:** the only global mutation in the queue. Blast radius checked: `instanceof Backbone.Model` / `instanceof Model` appears exactly five times in `public/scripts/{lib,app}` outside `parse-1.5.0.js` — `backbone.js:690`, `backbone.js:916`, and `backform.js:198/214/258` (all three guarding `this.model.errorModel`, never a Parse.Object). Marionette has none. Backbone's `extend` copies statics with lodash `_.extend` (own *string* keys), so `instanceof SomeSubclass` is untouched.

## 2. Restore `Collection.getByCid`

**Root cause.** `Backbone` 1.1.2 folded cid lookup into `_byId` and dropped the name (zero occurrences in `public/scripts/lib/backbone.js`), but `public/scripts/app/views/CharacterExperienceView.js` calls `self.collection.getByCid(...)` at lines 102, 127, 139, 152, 185, 187. Today those rows never render at all, so the missing method is masked; once item 1 lands, the first Edit/Delete click throws `self.collection.getByCid is not a function`.

**Change.** `public/scripts/lib/parse-compat/collection.js`, next to the existing `_byCid` getter at `:107`, verbatim from `parse-1.5.0.js:6663-6665`:

```js
getByCid: function (cid) { return cid && this._byCid[cid.cid || cid]; }
```

Put it in the `extend` literal (`collection.js:51`) — unlike `_byCid` it is a plain method, so `_.extend` copies it fine.

**Verify.** `npm run test:node` with a test asserting `c.add(obj); c.getByCid(obj.cid) === obj` and `c.getByCid({cid: obj.cid}) === obj`. Grep confirms the six call sites all key off `notation-id="<%= log.cid %>"` in `public/index.html`.

**Clears:** 2 — `character-history.spec.js:66` and `:99` — **but only with item 1**; alone it clears zero, because the notation rows are never emitted (`public/index.html:574, 589`).

**Risk:** near zero. Purely additive.

## 3. Restore `_serverData` and `_previousAttributes` on `ParseObject.prototype`

**Root cause.** `Character.update_troupe_acls` does `delete self._previousAttributes.troupes;` at `public/scripts/app/models/Character.js:920` and `delete self._serverData.troupes;` at `:921`; parse@8 has neither property (zero grep hits in `parse-8.6.0.js`; 18 in `parse-1.5.0.js`), so line 920 throws `TypeError: Cannot convert undefined or null to object`. The throw becomes a rejection inside a CompatPromise `.then`, `join_troupe` rejects, and `character_join_troupe`'s live `.fail` at `public/scripts/app/routers/mobileRouter.js:1875-1877` rewrites the hash back to `#character?<cid>` — exactly the observed end state.

**Parse 1.5 behaviour being restored.** `parse-1.5.0.js:4516` `this._serverData = {};` and `:4533` `this._previousAttributes = _.clone(this.attributes);` — unconditional own properties, so all four deletes were safe and were the documented way to purge a cached key (`:5169-5173`, `:5198`).

**Change.** `public/scripts/lib/parse-compat/events.js`, in `applyTo(ParseObject)` alongside the existing `cid` (`:77`) and `previousAttributes()` (`:197`) restorations. Two non-enumerable getters: `_serverData` delegating to parse@8's live `this._getServerData()` (`parse-8.6.0.js:43191` → `42980`, which returns the same mutable bag `estimateAttributes` reads, so the delete keeps working); `_previousAttributes` returning the existing `_compatPrevious` backing store (`events.js:164`, reassigned on each non-silent set, so it stays live).

Leave `Character.js:918` (`delete self.attributes.troupes`) alone — `attributes` is a frozen getter in parse@8 and `Character.js` has no `"use strict"`, so it silently returns false. Adding `"use strict"` to that file later would turn it into a TypeError; drop the line in a follow-up instead.

**Verify.** `npm run test:node` with a test in `test/parse-compat-events.test.js`: after `obj._finishFetch({objectId:'x', troupes:1})`, `delete obj._serverData.troupes` does not throw and `obj.get('troupes')` is `undefined`; `obj._previousAttributes` is an object, not `undefined`. Also fixes the second live reader at `Character.js:178` (`modified_trait._serverData.name`, currently swallowed by a try/catch that downgrades duplicate-name errors from code 1 to code 2).

**Clears:** 1 — `approvals.spec.js:528` (76). It is a `beforeAll`, so a whole suite currently stands behind it; the run only counts one.

**Risk:** near zero. Two non-enumerable getters on the prototype, both mapping onto live parse@8 state.

## 4. Unsaved-child pointer inside `Character.update_trait`

**Root cause.** parse@8 refuses to encode a parent holding an unsaved child — `toJSON` → `encode` → `toPointer`, "Cannot create a pointer to an unsaved ParseObject". Parse 1.5 tolerated it. (Handed to us as already diagnosed; I did not re-derive it.)

**Change.** *Not designed.* This is the honest state of the queue. Two shapes to evaluate before writing code, in `public/scripts/lib/parse-compat/` vs `public/scripts/app/models/Character.js`:
- compat: make the save path resolve unsaved children the way `saveAll` does, i.e. a pre-pass that saves pointees before encoding the parent — 1.5's implicit behaviour, but a real behaviour change against parse@8's deliberate guard;
- app: save the child explicitly in `update_trait` before setting the pointer.

Pick after reading the exact `update_trait` call path and the 1.5 `save`/`_deepSaveAsync` code; do not guess.

**Verify.** Node harness against real `parse-8.6.0.js`: build a parent with an unsaved child, call the same code path, assert no throw and that the child gets an `objectId` first. The seven specs all fail with a bare `page.waitForFunction: Timeout 30000ms exceeded` (`waitForHashToLeave`), which gives no signal short of a real run.

**Clears:** up to 7 — `admin-rules.spec.js:224` (16), `assets-rename-portrait.spec.js:425` (99), `descriptions-by-creature.spec.js:108` (287), `traits-lifecycle.spec.js:541` (241), `lifecycle-vampire.spec.js:291` (318), `lifecycle-werewolf.spec.js:286` (341), `lifecycle-changeling.spec.js:299` (361). See the attribution caveat below — some of these may already be gone after item 1.

**Risk:** highest in the queue, and the only item where the fix is unwritten. That is why it sits below three cheap certain wins despite clearing the most tests.

## Needs diagnosis first / still unknown

Nothing was refuted and nothing scored below confidence 6, so this section is open questions, not rejected work.

- **Attribution of the 7 timeouts is not clean.** Test 16 (`admin-rules`) was independently traced to a polluted `bnsmetv1_ClanRule` payload (`{"className":"bnsmetv1_ClanRule","_objCount":1,"__compatEventsApplied":true,…}`) — that is item 1's bug, not the unsaved-pointer bug. Test 287 (clan picker) reads the same data. So item 4's "7" may really be 5, or fewer. **Re-run and re-measure after items 1–3 before spending a session on item 4.** Do not design the item-4 fix against a stale failure list.
- **Blast radius of item 1 is unmeasured upward.** All 12 `Parse.Collection` subclasses are currently storing decoys on every `fetch`/`reset`. Some currently-*passing* tests may be passing by accident (the skeptic's read of "Can add a new XP notation entry" is that it survives on a render race, since `saveAll` does reject at `parse-8.6.0.js:44846`). Items 1–3 could move tests in either direction; the only honest measurement is a full run.
- **`always()` is eating rejections.** `parse-compat/promise.js:186` implements `always` as `then(cb, cb)`, so any `.fail(PromiseFailReport)` sitting *after* an `.always()` is dead code — that is why item 3's TypeError cost an entire suite silently. Do **not** change `always` itself (`promise.js:170-185` records that making those handlers live broke character creation). The cheap mitigation is moving `PromiseFailReport` ahead of the `.always` on the troupe routes. Unscoped.
- **`Character.js:242-245` swallows save failures** in a `.fail(function (errors) { … PromiseFailReport(errors); })` that returns `undefined` and resolves the chain, which is why `Vampire.create` "succeeds" over a rejected batch. Separate ticket; do not fold into items 1–4.
- **Two existing band-aids need re-examination after item 1**, not removal during it: the `cid` getter (`events.js:77`) and the `_byCid` getter (`collection.js:107`). Backbone genuinely needs `cid` and `Character.js:548` genuinely reads `_byCid`, so both stay — but their comments describe pathologies ("49 clans collapsing to 1", `_byId[undefined]` collisions) that were symptoms of the decoy bug and will read as false once it is fixed. The `_byCid` loop at `Character.js:546-552` is also dead weight (always yields index 0, in 1.5 too) and belongs in the codemod pass, not here.
- **Hardening, explicitly insufficient:** making `_compatPending` / `_compatPrevious` / `changed` / `__compatEventsApplied` non-enumerable (`events.js:144, 160, 164, 266`) shrinks the failure mode but does not fix it — `className`, `_objCount`, `_localId` are parse@8's own enumerables, and app code hangs enumerable instance props too (`Troupe.js:17` `title_options`, `Character.js:594` `recorded_changes`, `Character.js:1109` `_ltCache`). Do it, but not instead of item 1.
- **Stale comment, unverified premise:** `events.js:246-252` claims parse@8 "READS `__super__` and never sets it", but `parse-8.6.0.js:44468` does `ParseObjectSubclass.__super__ = parentProto`. Unrelated to these 18; someone should re-read that comment's justification.
- **Verification ceiling.** `npm run test:node` plus Node harnesses against the real vendored `parse-8.6.0.js` catch every mechanism above, but none of them exercise jQuery Mobile routing, so the four hash/visibility symptoms (03, 130, 388, 76) can only be *confirmed* by a real run. The cheapest real check is a single spec (`npm run test:e2e:xp`, `:longtexts`, `:approvals`), which still needs a server and a port — get an explicit serialized slot rather than firing it off alongside other agents.
